## 背景

Africa Book 不是 React monorepo，但它同样存在容易膨胀成审查负担的手写文件：`assets/css/landing.css`、落地页生成脚本、共享内容模块、模板，以及仓库本地工作流文档。仓库目前已经对本地化配对、OpenSpec、图表工作流和验证提出了明确要求，缺的是一条小而明确的规则，用来保持手写源码的可审查性，避免大文件无限增长。

参考仓库 `oae-mono` 已经给出了一个可迁移的模式：
- 用指导阈值而不是编译器式硬失败，
- 区分普通源码文件与特别容易膨胀的界面承载文件，
- 对特别大的新文件要求额外说明，
- 并避免让已经超大的文件继续无约束增长。

这个模式很适合迁移到 Africa Book，只需要把第二类对象从 React 路由页改成更贴合本仓库的高风险面：落地页样式表、站点模板和页面生成脚本。

## 目标 / 非目标

**目标：**
- 为手写源码文件增加一条以可审查性为导向的行数规则。
- 让规则直接覆盖本仓库最容易膨胀的面：样式表、模板和生成脚本。
- 保持规则务实：把它作为指导阈值加升级阈值，而不是对所有边界情况一刀切。
- 明确保留生成文件等无需手工优化行数的豁免项。

**非目标：**
- 不在本次变更中顺手重构所有已超限文件。
- 不引入自动强制文件大小的工具链。
- 不为仓库内每一种文件扩展名单独制定一套阈值。

## 决策

### 1. 用指导阈值，而不是硬性禁令

这条仓库规则应该在规划和编辑阶段指导代理行为，而不是变成构建阻断器。因此规则语言应使用“通常应当”来表达默认阈值，同时仍要求对极端情况给出明确说明。

### 2. 保留一个通用阈值和一个仓库特定的更严格阈值

本政策采用：
- 新建手写源码文件通用阈值 600 行，
- 落地页样式表、站点模板和页面生成脚本更严格的 500 行阈值，
- 任何新建手写源码文件的 800 行升级阈值。

这样规则既简单，也能直接击中 Africa Book 中最容易变得难以审查的文件类型。

### 3. 已超限的大文件不能继续被随手做大

真正有实操价值的规则，不只是限制新文件。对已经超限的文件，代理应避免继续增加其体量。若本次编辑并非纯机械性小改动，则应抽出至少一个有内聚性的部分样式、辅助模块、内容模块或脚本拆分，除非这会引入与当前任务无关的额外扰动。

### 4. 明确保留豁免项

生成文件、锁文件、快照、夹具数据、第三方参考文件，以及迁移类产物应继续豁免。这样规则才能聚焦在手写文件的可维护性，而不是机械惩罚构建输出。

## 风险 / 权衡

- [规则过严会拖慢紧急小修] -> 采用“通常应当”的指导语气，加上 800 行例外阈值，而不是绝对禁止。
- [仓库仍可能保留历史超大文件] -> 要求代理不要继续随手放大它们，并在非平凡编辑时至少抽出一个有内聚性的单元。
- [不同文件类型的代码密度不同] -> 只保留两档阈值，让规则更容易记住，也更容易实际执行。

## 迁移计划

- 在同一变更中同步更新 `AGENTS.md` 和 `AGENTS.zh_CN.md`。
- 通过现有工作流治理能力引用这条新规则。
- 不把对历史超限文件的清理重构塞进这次纯政策更新中。

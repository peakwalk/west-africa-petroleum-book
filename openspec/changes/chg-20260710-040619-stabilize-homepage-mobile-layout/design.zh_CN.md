## Context

landing 首页的结构标记其实已经有移动端菜单和紧凑品牌标识，但窄屏断点样式在几个关键区域里仍然表现得像桌面页。`390px` 下，header 继续显示桌面导航，`decision-strip` 继续保留桌面双列，英文 summary row 继续保留桌面四列；`320x568` 下，hero 指标区仍在 CTA 之前，紧凑品牌标识的点击面偏小，stakeholder / summary 模块也还带着桌面密度；`768x1024` 下，页面又进入了一种混合态，顶部仍是紧凑控件，但 hero 重新回到 CTA 落在 metrics 之后的桌面式顺序。第一轮竖屏平板补桥落地后，`768x1024` 的复审仍然不顺，因为整个页面更像被放大的手机布局，而不是竖屏平板布局。随后在 `1023px` 与 `1024px` 边界继续复审时，又暴露出第二层断点问题：紧凑平板 header 与 logo 处理还在，但 hero 和 summary 的密度切换时机已经与其他区块脱节，整页没有再作为一个系统同步进入桌面态。

headless Playwright 截图给出的证据很具体：

- `390px`：`document.documentElement.scrollWidth` 扩大到 `477px`
- `390px`：`.decision-strip-inner` 和 `.decision-strip-copy` 仍然解析成双列
- `390px`：`.section-summary-modules .summary-grid` 仍然解析成四列
- `320x568`：hero 主 CTA 被推到了首屏很下方
- `320x568`：紧凑品牌标识的点击区域大约只有 `32x44`，低于期望的触达面
- `768x1024`：hero CTA 在 metric grid 之后缩成了行内宽度按钮，而没有继续留在窄屏阅读轨道上
- 第一轮补桥后的 `768x1024`：hero CTA 横条几乎占满整条内容宽度，指标区仍然占据过重首屏面积，audience 卡片则落在一个中间留白过大的稀疏双列网格里
- `~1024px` 宽度下的 summary 复审：`Latest Updates`、`Current Edition`、`Topics Covered` 和 `Future Development` 仍然四列并排，因为平板覆盖用的是比桌面 `.section-summary-modules .summary-grid` 更弱的选择器
- `1023px`：移动/平板 header 控件仍然激活，但 hero CTA 轨道已经提前塌回更接近桌面的行内操作节奏
- `1024px`：桌面导航和更高密度的多列区块已经恢复，但 summary row 仍停留在平板双列状态，说明平板与桌面的边界被不同模块拆开了
- `320px`：小手机 hero 已经不再溢出，但标题仍然贴得过近，右侧安全边距不够
- `767px`：手机上边界虽然稳定，但 countries、topics 和 summary 模块在进入平板前 1px 仍保持单列，导致视觉密度明显偏稀
- `1119px`：宽平板 hero 虽然保住了正确的阅读顺序，但固定宽度的内容 / 操作轨道在桌面切换前已经开始显得左重

用户给的 header 参考图又增加了一个明确约束：窄屏 header 应该呈现为左对齐的紧凑品牌标识，加上右对齐的控制组，控制组由语言切换胶囊、圆形联系按钮和菜单胶囊组成。现有 landing CSS 已经有 `.header-contact-link`，因此最窄实现路径不是发明新模式，而是把这个缺失控件真正接进生成后的 header，并收紧手机断点行为。

仓库还要求 landing 样式文件保持可审阅的体量，所以最终方案不能继续把所有手机逻辑都堆进一个不断膨胀的 responsive 文件里。

## Goals / Non-Goals

**Goals:**
- 去掉 landing 首页在手机宽度下的横向溢出。
- 启用已经存在的移动端 header 导航方案，而不是在手机上继续显示桌面导航。
- 让手机 header 控制组对齐用户提供的参考图，包括独立联系按钮，以及不再出现品牌文字重叠。
- 让主 hero CTA 在手机宽度下出现在 metric grid 之前，在小手机上仍保持靠近首屏，并避免为 `<=360px` 单独切出第二套 hero 阅读顺序。
- 让 hero CTA 在 `768px` 到 `860px` 的竖屏平板过渡带中也继续先于 metric grid，避免页面在手机/平板断点处跳成混合态。
- 让 landing 布局在 `861px` 到 `1119px` 之间继续保持系统化的平板表现，让 header 控件、hero 密度和区块网格仍然作为同一套平板语言工作。
- 让 `decision-strip` 在手机宽度下干净地折叠，同时让 stakeholder 卡片保持足够紧凑，避免区块过高。
- 让英文 summary 区块在手机宽度下可读，不再继承桌面固定卡片高度。
- 明确把桌面起始点放到 `1120px`，让导航、logo 间距、hero 密度和区块网格一起切换。
- 补上回归检查，避免这些手机断点覆盖规则再次丢失。

**Non-Goals:**
- 不重做桌面或平板版 landing 体验。
- 不修改首页文案、路由或区块顺序。
- 不重做法文兼容首页主体结构，除非它自然受到共享 mobile CSS 的影响。
- 不重新打开 footer 布局问题，除非新的手机证据表明它仍在溢出。

## Decisions

### Decision: 在 `landing.responsive-mobile.css` 中保留共享手机基础规则，并把首页专属规则拆到独立 partial
现有标记已经暴露出需要的移动端 header 控件和区块包装器。可持续的修复方式，是把共享 header / 通用手机基础规则留在 `assets/css/landing.responsive-mobile.css`，同时把首页专属的手机行为拆到 `assets/css/landing.responsive-mobile-homepage.css`，这样既能修复问题，也能继续满足仓库对样式文件体量的约束。

备选方案：
- 直接补丁生成后的 `public/*.html`。拒绝，因为生成文件不是事实来源，下次构建会被覆盖。
- 把所有新增规则继续塞进同一个 responsive 文件。拒绝，因为 `landing.responsive-mobile.css` 会超过仓库允许的可审阅尺寸。

### Decision: summary grid 覆盖要匹配桌面选择器优先级
桌面 summary 布局来自 `.section-summary-modules .summary-grid`。因此手机端覆盖必须使用同样带区块限定的选择器，不能只写 `.summary-grid`，否则即便源顺序更靠后，桌面规则仍会继续生效。

备选方案：
- 给手机端 grid 规则加 `!important`。拒绝，因为直接匹配既有选择器优先级更干净，也更容易维护。

### Decision: 手机上复用平板已有的移动菜单显示模式
平板样式已经会隐藏 `.primary-nav` 并显示 `.header-actions` 与 `.mobile-nav-menu`。手机断点应该明确沿用这套行为，而不是再造第三种导航模式。

备选方案：
- 保留桌面导航，只继续压缩间距。拒绝，因为当前手机截图已经显示这些链接会把 header 挤乱，并加剧布局不稳定。

### Decision: 复用现有 header 联系按钮样式和现有邮件图形
landing 样式里已经定义了 `.header-contact-link`，reader toolbar 里也已经有与项目线性图标语言一致的邮件图形。最窄的修复方式，就是在 `scripts/shared/landing-shell.mjs` 中真正渲染这个联系入口，在手机断点隐藏品牌参考文字，并让 mobile 规则把右侧三个控件排成一个一致的 action 组。

备选方案：
- 新增一个只在手机上显示的文字版 Contact 胶囊。拒绝，因为参考图明确是圆形图标按钮，而且 header 宽度也比桌面文字 CTA 更紧。
- 继续把联系入口只放在下拉菜单里。拒绝，因为用户给的参考图要求它在顶栏第一行就可见。

### Decision: 通过 CSS 重排 hero，而不是改首页 DOM 顺序
hero copy block 的 DOM 结构已经稳定。对于手机来说，风险最小的做法是把 `.hero-copy-block-v2` 变成 flex column，让 supporting copy、CTA 和 metric grid 保持在同一条阅读轨道上，并让 CTA 区块出现在 metric grid 之前。到了小手机宽度，持久方案是继续收紧这条轨道的宽度与间距，而不是再引入第二套 hero 顺序。

备选方案：
- 直接改写 `scripts/shared/homepage-content.mjs` 中的标记顺序。拒绝，因为桌面和平板当前都依赖现有 DOM 顺序正常工作。

### Decision: 平滑小手机断点，而不是为 `<=360px` 分叉第二套移动模板
第一轮手机修复去掉了溢出，但后续对 `320x568` / `360x640` / `390x844` 的截图又暴露出新的断点跳变：`390px` 仍然是 copy 在 CTA 前，而 `360px` 却切成了 CTA-first hero；`320px` 下 copy/stat 区块又比 CTA 更靠右；mobile menu panel 的左右内边距不对称；Current Edition 卡片在封面下堆后也显得过空。可持续的修复方式，是让 `320px` 到 `390px` 共享同一套 hero 阅读顺序和内容内边距轨道，让 `.mobile-nav-panel` 对齐这套 gutter，并保留紧凑的 inline edition-card 布局。

备选方案：
- 保留 `<=360px` 的特殊 hero 顺序与封面下堆版式。拒绝，因为它会让相邻手机宽度之间出现明显结构跳变，也会在 summary 区块里浪费纵向空间。

### Decision: 增加窄竖屏平板过渡层，而不是整体移动平板断点
`768px` 断点本身已经承载了被批准的平板 header / logo 处理。当前回归并不是这个断点存在，而是它一旦生效，hero 就立刻退回到偏桌面的顺序。风险最小的修复方式，是在 `landing.responsive-tablet.css` 中增加一层 `768px` 到 `860px` 的覆盖：保留平板 header 处理，同时把 hero 拉回纵向阅读轨道，让 CTA 继续排在 metric grid 之前。

备选方案：
- 把整个移动端断点从 `767px` 直接提升到 `860px`。拒绝，因为这会把已经批准的平板 header 和其他平板网格也一并压回手机表现。
- 在所有宽度上重写首页 DOM 顺序。拒绝，因为桌面和更宽的平板布局已经依赖当前标记顺序正常工作，真正需要补桥的只是窄竖屏平板这段范围。

### Decision: 让竖屏平板补桥看起来像平板，而不是像手机
第一轮补桥解决了顺序 bug，但视觉复审表明，如果继续沿用手机式的满宽 CTA 横条和稀疏双列 stakeholder 布局，`768x1024` 仍然会显得别扭。更合理的竖屏平板处理方式，是保留纵向 hero 阅读顺序，但把内容轨道收窄，CTA 改成中等宽度的操作条，同时把指标区和 stakeholder 区都调整成更紧凑的 `3 x 2` 网格，让整页在这个断点下更像平板而不是放大的手机。

备选方案：
- 保留手机式满宽 CTA 横条。拒绝，因为它会让 hero 显得过大，并把过多视觉重量推回首屏。
- 保留双列 stakeholder 布局。拒绝，因为固定宽度卡片会在中间留下很大的空白，让区块看起来没有收口。

### Decision: 增加 `861px` 到 `1119px` 的宽平板过渡层，并把桌面起始点后移到 `1120px`
`1023px` / `1024px` 的复审说明，当前断点模型仍然会把页面切成互不兼容的状态。风险最小的修复方式，是把紧凑平板 header 处理保留到 `1119px`，同时为 `861px` 到 `1119px` 增加第二层平板过渡，保持平板密度的 hero / actions / metrics 以及 `3 x 2` audience 卡片，并将小桌面 header / nav 的起始点后移到 `1120px`，让真正的桌面布局作为一次协调一致的切换出现。

备选方案：
- 保留 `1024px` 的桌面起始点，只补 hero CTA 宽度。拒绝，因为复审暴露的是多个区块在不同宽度各自切换，而不只是 hero action 行的问题。
- 只把 summary row 在 `1024px` 拉回桌面。拒绝，因为这只会保留不一致的边界，而不是消除它。

### Decision: 增加 `700px` 到 `767px` 的大手机过渡层
第六次评审表明，最后一段手机断点虽然技术上稳定，但视觉上已经显得过稀。最小修复方式，是保持紧凑手机 header 和 hero 行为不变，只让首页内容网格在 `700px` 到 `767px` 之间先收敛为双列。这样可以减少过多的纵向留白，同时又不需要提前进入平板 header 模式。

备选方案：
- 保持所有手机宽度到 `767px` 都是单列。拒绝，因为 `767px` 的截图相较紧邻的 `768px` 平板视图显得明显过稀。
- 把完整平板断点提前到 `768px` 以下。拒绝，因为这会重新打开已经批准的平板 header 切换点。

### Decision: 增加一个 `<=320px` 的 hero 标题微调层
小手机 hero 轨道大体已经修复，但最新评审仍然测到 `320px` 标题存在负的右侧留白。最窄的修复方式，是只在 `<=320px` 增加一层轻量的标题字号与行长调整，而不动其余已经稳定的 copy / CTA / stats 轨道。

备选方案：
- 把标题缩小规则扩大到整个 `<=360px` 区间。拒绝，因为 `360px` 的右侧边距已经处于可接受范围。
- 再次整体收紧小手机内容轨道。拒绝，因为 CTA、copy 和 stats 的对齐已经正确。

### Decision: 让宽平板 hero 轨道随视口轻微放大
`861px` 到 `1119px` 的宽平板补桥已经解决了混合态，但固定的 `33rem` CTA 轨道和固定的内容上限，让 hero 在 `1119px` 附近开始出现明显左重。进一步收口的方式，是保留同样的纵向平板阅读顺序，但通过 `clamp(...)` 让 copy、actions 和 stats 轨道在这段宽度里轻微随视口增长，从而在 `1120px` 真正切回桌面前维持更均衡的重心。

备选方案：
- 保持到 `1119px` 都是完全固定宽度。拒绝，因为评审已经证明桌面切换前仍存在明显的平衡问题。
- 在 `1120px` 之前更早切回桌面式行内 CTA 节奏。拒绝，因为这会把这组变更正在消除的混合态重新带回来。

### Decision: 通过带区块限定的 summary-grid 覆盖把这组卡片在 `1119px` 及以下压成两列
summary 模块的复审暴露出另一类断点问题：平板样式表虽然已经尝试把 `.summary-grid` 改成两列，但桌面布局来自 `.section-summary-modules .summary-grid`，因此更弱的平板选择器在优先级上输了，卡片在 `1024px` 及以下仍然继续四列并排。既然桌面起始点要后移到 `1120px`，最小修复方式也要一起扩到 `1119px`：补一层带区块限定的平板覆盖，明确把 summary grid 改成两列，并移除桌面固定最小高度假设，让卡片按内容高度对齐。

备选方案：
- 保留泛化的 `.summary-grid` 平板规则，只依赖源顺序覆盖。拒绝，因为桌面选择器优先级更高，仍会继续获胜。
- 用 `!important` 强行压出两列。拒绝，因为直接匹配选择器优先级更干净，也更容易维护。

### Decision: audience 卡片在手机上改成更紧凑的双列，而不是单列长栈
桌面端的六列 stakeholder row 不能原样保留，但如果手机上改成一列一张卡，会把这个区块拉得过高。双列手机网格配合弹性卡片尺寸，能在不牺牲可读性的前提下控制页面纵向长度。

备选方案：
- 保持单列手机栈。拒绝，因为它只会增加滚动深度，并不会提升理解效率。

## Risks / Trade-offs

- [窄屏选择器更新可能误伤更宽的平板布局] -> 手机规则继续限制在 `@media (max-width: 767px)` 中，竖屏平板补桥只限制在 `@media (min-width: 768px) and (max-width: 860px)`，宽平板补桥只限制在 `@media (min-width: 861px) and (max-width: 1119px)`，从而让每一段平板行为都保持显式。
- [summary grid 修复可能误伤法文兼容区块] -> 将单列覆盖限定在 `.section-summary-modules .summary-grid`，只命中英文 summary row。
- [header 控件切换若不完整，可能导致导航被整体隐藏] -> 扩展验证，断言手机 header 代码块里同时存在“隐藏桌面导航”和“显示移动端控件”的规则。
- [CTA 优先级调整可能让 hero 信息被隐藏] -> 保留所有 hero 文案；小手机只收紧间距与 gutter，不切换成另一套 hero 模板。
- [桌面起始点后移可能让较小横向平板延后进入高密度布局] -> 在 `860px`、`861px`、`1023px`、`1024px` 和 `1120px` 明确做边界验证，确保新的切换点在每个过渡宽度上都仍然显得合理。

## 新增需求

### 需求：落地页样式源码必须模块化，同时保持公开入口不变
仓库必须继续保留 `assets/css/landing.css` 作为生成 HTML 使用的公开落地页样式入口文件，但手写的落地页样式源码必须组织成多个更小、更有内聚性的模块，而不是继续维持一个持续膨胀的单体样式文件。模块化后必须保持现有资源引用方式和首页渲染行为不变。

#### 场景：生成 HTML 保持相同的 landing 样式路径
- **当** 站点生成器渲染英文或法文首页时
- **则** HTML 仍然引用 `assets/css/landing.css` 作为公开的落地页样式入口文件

#### 场景：模块化源码保持首页渲染行为
- **当** 落地页样式源码被拆分为更小模块时
- **则** 最终首页渲染仍保持拆分前相同的预期视觉行为和资源解析方式

### 需求：落地页样式验证必须针对展开 import 后的 CSS 执行
如果 `assets/css/landing.css` 变成一个很薄的 import 清单，那么落地页样式验证在检查预期选择器和声明之前，必须先展开本地 imports，这样断言语义才能与拆分前保持等价。

#### 场景：拆分后断言仍能看到 hero 和 header 规则
- **当** 站点渲染验证在模块化之后检查 landing CSS 时
- **则** 验证会先展开被 import 的 landing CSS 模块，再检查预期的 header、hero、导航和响应式声明

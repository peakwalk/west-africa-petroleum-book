## 背景

落地页通过静态 HTML shell 发布，并引用 `assets/css/landing.css?v=20260701`。这个样式文件现在已经成为首页主要的手写样式面，并且堆积了多个不同职责：
- 全局 tokens 和布局基础规则，
- header 和移动导航，
- hero 布局与 hero 变体，
- 通用 section 和卡片样式，
- discovery 与 summary 模块，
- footer 样式，
- 以及响应式覆盖。

仓库刚新增的文件大小指导要求落地页样式文件通常应控制在 500 行以内，并要求对已经超限的大文件做非平凡编辑时抽出有内聚性的部分。要在不改变公开行为的前提下满足这条规则，最安全的做法是保留 `landing.css` 作为一个很薄的 import 入口文件，并把现有规则移动到同目录的多个模块文件中，这样相对资源路径仍然可以继续工作。

`scripts/test-site-render.sh` 当前大量直接读取 `assets/css/landing.css` 做断言。如果入口文件变成 import 清单，验证脚本就必须先展开这些 import，再对合并后的 CSS 字符串执行现有检查。

## 目标 / 非目标

**目标：**
- 把 `landing.css` 缩减成一个很小的入口样式文件。
- 按仓库新的大小指导把手写 CSS 拆成多个有内聚性的模块。
- 保持现有资源路径、样式 URL 和首页渲染行为不变。
- 拆分后维持同等强度的验证。

**非目标：**
- 不重新设计首页。
- 不修改公开的样式文件 URL。
- 不引入新的 CSS 构建流水线或预处理器。
- 不借这次拆分顺手做大范围视觉清理。

## 决策

### 1. 保持公开入口稳定

`assets/css/landing.css` 继续作为生成 HTML 唯一引用的样式文件。它会变成一个 import 清单，因此不需要改模板或资源版本逻辑。

### 2. 按稳定职责边界拆分

样式文件将拆成这些同级模块：
- 基础 tokens 与基础规则，
- header 与导航，
- hero，
- 通用 section 与卡片，
- discovery 与 summary 模块，
- footer，
- 响应式覆盖。

这些边界更符合首页真实演化方式，也比单纯按行数硬切更容易维护。

### 3. 模块与入口文件保持同目录

新的拆分样式文件继续放在 `assets/css/` 下，与 `landing.css` 同级。这样就不需要为子目录迁移重写所有 `url("../images/...")` 与 `url("../icons/...")` 资源引用。

### 4. 验证对象应是展开后的 CSS，而不是薄入口文件本身

站点渲染脚本应先沿着本地 `@import` 规则重建一份合并后的 landing CSS 字符串，再对其中的选择器和声明执行现有断言。这样可以保持当前断言的真实含义不变。

## 风险 / 权衡

- [import 顺序出错会造成样式回归] -> 拆分时严格保持原有源码顺序，并用 `build:site` 和 `test:site` 验证。
- [如果验证只看入口文件，会削弱检查强度] -> 先展开 import，再对合并后的 CSS 文本执行断言。
- [某些模块拆完后仍可能超出新规则] -> 预留足够数量的模块，让每个手写样式文件都明显低于阈值。

## 迁移计划

1. 为样式组织重构补齐 OpenSpec 文档。
2. 把 `landing.css` 拆成有顺序的同级模块，并把入口文件缩减为 imports。
3. 更新 `scripts/test-site-render.sh`，让它验证展开后的 CSS 内容。
4. 运行 `npm run build:site` 和 `npm run test:site`。
